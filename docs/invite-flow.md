# Plan: Invite Flow & Role-Based Access Redesign

## Context

The app is a coach-first SaaS where clubs buy licences and get onboarded by the platform admins. The current UX has two problems:

1. **Confusing invite flow**: new users hit the home page with no direction; org and team invite codes are buried in the profile page with no clear separation — players and coaches see the same dual join-org / join-team UI even though their journeys are totally different.
2. **No role-based access**: players see Library, Upload, and Playlists creation even though they should only be viewers of playlists sent to them.

The goal is a coherent, role-aware product: admin sets up the org, coaches run the operation, players are passive viewers.

## Invite Code Design ✅ Decisions locked

Two invite code types, not three separate flows:

**Org invite code** (6-char, in `org_invites`)
- Roles: `admin`, `coach`
- Generated by: platform admin (admin codes); org admin **or coach** (coach codes)
- Effect: joins org + sets role. Coaches then join teams manually by browsing org teams.

**Team invite code** (6-char, in `team_invites`)
- Role: `player` only
- Generated by: coach or org admin, scoped to a specific team
- Effect: joins org as `player` AND joins that specific team **atomically in one RPC**
- Rationale: players have no reason to pick a team — the invite IS the team assignment.

This replaces the current confusing four-path (org coach, org player, team coach, team player) with two clear paths: *coaches/admins use org codes, players use team codes.*

## Onboarding Flow

**Industry precedent:** Slack, Notion, Linear all gate first use behind a team/workspace join. Code-entry after email verification is standard practice.

```
Sign up → Verify email → App opens → [no org?] → Onboarding screen → Enter code → Home
```

The onboarding screen replaces the scattered "create org / join org / join team" UI currently buried in the profile page. It is the **only** entry point for new users.

- No "create org" option for regular users — admins are bootstrapped by platform admin.
- Single input accepts either an org code (for coaches/admins) or a team code (for players).
- The backend auto-detects the code type: try `org_invites` first, then `team_invites`. One RPC handles both.
- After joining, redirect to role-appropriate home.

## Player Home / My Playlists

Players need a view to see playlists that have been sent to their team. Currently, "send to players" = Clip & Ship to R2, but there's no player-facing view.

The mechanism: playlists assigned to a team (`team_id` on the playlists table) are visible to all members of that team. This is already half-implemented (team assignment exists as metadata); it just needs:
1. RLS on `playlists` extended: members of the assigned team can SELECT.
2. A player-facing "My Playlists" view that shows only team-assigned playlists for the player's teams.

## Implementation Phases (High-Level)

### Phase A — DB
1. New RPC `join_by_code(code)`: detects org vs team code, handles both cases atomically for players (org join + team join in one transaction). For coaches it's just org join (same as current `join_org_by_code`).
2. Update `team_invites` join RPC to also set `org_id` when the user has none (currently it doesn't).
3. RLS update on `playlists`: add policy allowing team members to SELECT playlists where `team_id = their team`.
4. New RPC `promote_to_admin(p_user_id uuid)`: org admin promotes a coach in the same org.
5. Coach-level invite generation: update `generate_org_invite` RLS to also allow `role = 'coach'` callers (currently admin-only).

### Phase B — Types & DB layer
- New `join_by_code` function in `profile-db.ts`
- Update `generateOrgInviteCode` to be callable by coaches (role guard is server-side, client just calls it)
- `promoteToAdmin(userId)` function in `profile-db.ts`
- `getMyTeamPlaylists()` in `playlists-db.ts` (player-facing query)

### Phase C — Routing & Onboarding
- New `/onboarding` route in `App.tsx`
- New `src/pages/onboarding.tsx`: single code input, calls `join_by_code`, redirects on success
- Update `ProtectedRoute`: check `profile.orgId` and `profile.role` to enforce redirect rules

### Phase D — Sidebar & Nav
- Update `app-sidebar.tsx`: role-aware nav items (hide Library/Upload/Playlists create for players)

### Phase E — Profile Page
- Remove create-org + join card
- Add org member list for admins with "Promote to admin" button
- Add coach-level invite generation (coaches can now generate coach/player org invites)

### Phase F — Player Playlist View
- Home page: players see team playlists instead of empty "import a game" state
- Playlists page: players get a read-only view (no create, no edit, no clip-and-ship)

## Decisions

| Decision | Choice |
|---|---|
| Player invite type | Team code only — one code joins org as player + that specific team atomically |
| Who can generate invites | Org admin AND coaches (server-side guard, no client changes to wire) |
| Player playlist delivery | Team assignment — playlists assigned to a team auto-appear in player's My Playlists |

**Already-existing users**: users who already have `org_id` skip onboarding and land on home as today. Only `org_id = null` users hit the onboarding screen.
